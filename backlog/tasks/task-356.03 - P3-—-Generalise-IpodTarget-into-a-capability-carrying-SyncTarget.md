## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
doc-039 §"Device axis". The current `IpodTarget` abstraction is iPod-only and hardwired to model `MA147`; `TargetOptions` carries only `name`. Device is therefore not an axis anywhere. This is the prerequisite for device-as-an-axis and the largest single piece of the strategy.

## Scope

Replace `IpodTarget` with a `SyncTarget` abstraction covering both iPod and mass-storage devices:
- `kind: 'ipod' | 'mass-storage'`, optional `model`, and a `capabilities` snapshot (supported codecs, artwork storage model, artworkMaxResolution, video support).
- A normalised `getTracks(): TrackInfo[]` working for both backends — iPod via `@podkit/gpod-testing`, mass-storage via filesystem walk + ffprobe.
- Factory construction from existing capability sources: `@podkit/compatibility` `TESTABLE_MODELS` (iPod), `@podkit/devices-mass-storage` `BUILT_IN_PRESETS` (mass-storage).
- Mass-storage targets generate the bespoke `[devices.test] type=…` TOML currently hand-rolled in `codec-preference.test.ts` / `mass-storage-sync.test.ts`.

Keep `IPOD_TARGET=real` working (real device stays a SyncTarget of kind ipod). Does NOT add device as a matrix axis yet — that's P4. This task only delivers the abstraction + unit/smoke coverage that both backends report correct capabilities and track listings.

Can proceed in parallel with P2; P4 depends on both this and P1.

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
## What landed

- `targets/sync-target.ts` — `SyncTarget` interface (`kind`, `path`, `name`, `isRealDevice`, `model?`, `capabilities`, `deviceConfig()`, `getTracks()`, `cleanup()`) + `ipodCapabilitiesForModel(modelNumber)` deriving `DeviceCapabilities` via `@podkit/devices-ipod` `identify()` + `getCapabilities()` (same generation tables podkit ships).
- `targets/mass-storage.ts` — `MassStorageTarget`: temp dir + a `@podkit/devices-mass-storage` `BUILT_IN_PRESETS` preset. `getTracks()` walks the preset's `contentPaths.musicDir` and ffprobes each file into the same `TrackInfo` shape the iPod targets return. `deviceConfig()` emits the `[devices.<name>] type=<preset> path=<root>` block.
- `targets/types.ts` — `IpodTarget` now `extends SyncTarget` (adds `kind:'ipod'`, `getTrackCount`, `verify`); `TargetOptions` gains optional `model`.
- `targets/dummy.ts` / `targets/real.ts` — gain `kind`, `model`, `capabilities` (via `ipodCapabilitiesForModel`), `deviceConfig()` (returns null — iPods are path-addressed/auto-detected). Dummy threads `model` into `createTestIpod`.
- `targets/factory.ts` / `index.ts` — `createMassStorageTarget` + `withMassStorageTarget`; re-export `SyncTarget`/`DeviceConfigFragment`/`MassStorageTarget`/`ipodCapabilitiesForModel`.
- `targets/sync-target.test.ts` — smoke tests both backends.
- `package.json` — added `@podkit/device-types`, `@podkit/devices-ipod`, `@podkit/devices-mass-storage` workspace deps.

## Notes on the ACs

- AC#3 "factory builds from TESTABLE_MODELS": the factory accepts a `model` number and resolves caps from the devices-ipod tables (the same data TESTABLE_MODELS draws from). Iterating TESTABLE_MODELS as a device axis is P4; P3 delivers the per-model construction path.
- AC#1 "replace IpodTarget": done as `IpodTarget extends SyncTarget` rather than a rename, so the ~20 existing `withTarget` consumers keep compiling/passing (AC#6). SyncTarget is the canonical abstraction; IpodTarget is its iPod specialisation.
